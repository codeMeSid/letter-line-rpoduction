## Decisions and rationale

- **One agent per product, in parallel.** The five factories are independent folders following the same pattern, and the time budget was short. Parallel work was the fastest route.
- **Agents must not touch shared files** (`factories/registry.ts`, `docs/`, `factories/shared/`, `engine/`, other factories). This avoids write conflicts between parallel agents. The orchestrator does registry wiring and docs updates once, after all agents finish.
- **Template = `factories/bottle/`.** It is the most recent, reviewed factory and uses the shared `stationKit.ts` and `railRobot.ts`. Each new factory mirrors its structure:
  - `index.ts`
  - `visual.ts` (pure, with stages) plus `visual.test.ts`
  - `product.ts` plus `product.test.ts`
  - `stations/*.ts`, one file per station
  - `stations.test.ts` and `e2e.test.ts`
  - Last station `robot` wraps `railRobot(id, beltTip, shelfTip)`.
- **Product concepts given to the agents.** Each factory should have about 10–13 real stations.
  - **Cookie:** mixer, dough extruder/cutter, chip depositor, oven, cooling, packing. The character is piped in icing.
  - **Donut:** mixer, depositor, fryer, glazer/sprinkler, cooling, box. The donut is shaped like, or bears, the character.
  - **Mug:** clay mixer, slip casting/jigger, handle attach, dryer, glaze dip, kiln, decal/print, inspection.
  - **Can:** coil uncoiler, cupping press, draw-and-iron, trimmer, washer, printer/decorator, necker, filler, seamer.
  - **Car** (kind id `'car'`): plastic pellet hopper, injection moulding, sprue trim, wheel/axle assembly, paint, decal, box. The character appears as livery or a number.
- **Registry wiring is trivial.** `FACTORIES` in `factories/registry.ts` is `Partial<Record<ProductKind, FactoryDef>>`, and `PLOTS` derives built and unbuilt plots from it. Adding a kind to `FACTORIES` turns its construction site into a built factory automatically. `PRODUCT_KINDS` in `engine/types.ts` already lists all seven kinds: `['letter','bottle','cookie','donut','mug','can','car']`.
- **No commits.** The user's rules allow commits only when the user asks, using the caveman-commit style. Typecheck, test and build must all pass before any commit.

## Pitfalls

- **Placeholder visuals are rejected.** The user rejected the old Task 5 demo line as placeholder boxes. Every station must be a recognisable machine, and the product must visibly change shape across stages.
- **Conventions an agent may break.** Check each new factory for these:
  - Meshes only via `looks.part(geom, role)` (stations never use `own()`, ruling R16).
  - No `new *Material` outside `engine/looks.ts`.
  - Relative imports only under `factories/`, because vitest has no `@/` alias.
  - Letters only through `engine/glyphs.ts` `letterGeometry`, never fonts or TextGeometry.
  - World is z-up. The station frame has z=0 at the belt top (`BELT_TOP` 22) and the floor at z=−22.
  - One rAF loop only.
  - Particles only while a station processes a non-space job.
  - Sound only via `audio/bus.ts`.
- **Shared files.** Parallel agents were told not to touch shared files. If one did anyway (registry, shared, engine), reconcile it carefully and don't blindly overwrite.
